# Context Mesh Framework

Context Mesh keeps project intent, technical choices, implementation knowledge, and agent guidance separate so future work can use the right context without mixing requirements with code.

## Framework Overview

Context Mesh has three steps:

1. **Intent** — describe what the project and features do, why they exist, and their user value.
2. **Build** — implement changes using approved decisions and reusable patterns through Plan, Approve, Execute.
3. **Learn** — record outcomes, lessons, and evolution so future work starts from current knowledge.

## File Type Separation

- **Features** in `context/intent/feature-*.md` contain only What, Why, and functional acceptance criteria. They do not contain library names, file paths, code examples, or implementation mechanics.
- **Decisions** in `context/decisions/` contain technical choices, architecture, rationale, constraints, alternatives, and outcomes. They answer how the project chose to work.
- **Knowledge** in `context/knowledge/` contains reusable implementation knowledge. Patterns contain code conventions, examples, and how-to guidance; anti-patterns record approaches to avoid.
- **Agent files** in `context/agents/` contain role-specific guidance and do not replace intent, decisions, or patterns.
- `context/intent/project-intent.md` describes the project at a high level.
- `context/evolution/changelog.md` records context evolution and documented state.

Do not duplicate information across file types. Link between files when a feature relies on a decision or pattern.

## Plan, Approve, Execute

1. **Plan** — load project intent and relevant feature, decision, and pattern files.
2. **Approve** — record or confirm the technical decision before implementing a new approach.
3. **Execute** — implement the approved plan, follow patterns, run checks, and update context.

For existing-code documentation, analysis is the Plan and inferred existing choices are recorded as Accepted decisions; no new behavior is implied.

## When to Create Files

Create a file for durable knowledge: a user-facing capability, non-obvious technical choice, reusable implementation pattern, explicit anti-pattern, agent instruction, or meaningful evolution event. Do not create files for transient debugging notes, trivial details, or duplicated information; update the appropriate existing file instead.

## Context Structure

```text
context/
├── .context-mesh-framework.md
├── intent/
│   ├── project-intent.md
│   └── feature-[name].md
├── decisions/
├── knowledge/
│   ├── patterns/
│   └── anti-patterns/
├── agents/
└── evolution/
    └── changelog.md
```

## Definition of Done

- Relevant intent, decision, and pattern files are loaded.
- A decision exists before implementing a new technical approach.
- Feature, decision, and pattern content remains separated.
- Code follows accepted decisions and documented patterns.
- Appropriate tests and quality checks pass.
- Bidirectional links are added where relationships exist.
- Status sections are present and accurate.
- Context, including the changelog and decision outcomes, is updated after implementation.

## Bidirectional Links

Use relative Markdown links. Features link to applicable decisions and patterns. Decisions link back to features and related decisions. Patterns link to related decisions and features. Keep links valid when files are renamed.

## Status Requirements

Every context document has a `Status` section with a creation date and current state. Use `Active` for current knowledge, `Accepted` for technical decisions, and an explicit note when content was inferred from an existing implementation.
